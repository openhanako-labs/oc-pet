> 作者：奥菲莉娅（Ophelia）

> 关联：`projects/local-rlcd`（本地决策引擎）· `docs/本地决策引擎接入计划-2026-09-19.md`（本层是该计划 P1 动作选择的实现）

## 0. 一句话结论

**主 LLM 定情绪，本地引擎在同情绪的候选组里挑具体表情预设。**

分工的边界是实测划出来的，不是设计出来的：本地 1.5B 模型**理解中文对话很差**（中性句一律判「惊讶」，prob 还能到 1.0），但在**已经知道情绪**的前提下，从一组语义清晰的候选中挑细节动作**很准**（10/10，~100-300ms）。

所以它不做「读懂用户」，只做「翻译情绪到动作」——那一跳原来靠人手写的 22 条别名表，现在换成一次结构化决策。

---

## 1. 它治什么病

`avatar/live2d_renderer.py` 里有一条实测记录：

> 把 53 个预设名 + 13 个 motion 名（共 66 个）挤成一行塞进 prompt，
> `[do:]` **全历史 0 次使用**。

后来做了 `_AI_DO_ALIASES`（22 个中文语义标签 → 预设名）绕过去。但那是**给 LLM 猜**：LLM 说「害羞」，代码映射到 `blush_shy`。LLM 并没有真的在选动作，它只是在描述情绪；中间那一跳靠的是人手维护的映射表——**加一个新预设，得手动补一条别名**。

本层把这一跳换成决策：给引擎一份带中文语义标签的候选清单，让它直接挑。

**收益**：
- 53 个预设全部可点，不再受 22 条别名表限制
- 候选集按情绪动态收窄，引擎只需在同情绪的十来个候选里分辨
- 决策可观测（`decision_trace` 记录「选了什么、为什么」）

## 2. 架构

```
用户输入
   ↓
主 LLM（Hana）        ← 读懂对话，输出 [feel:v,a] / emotion 标签
   ↓  情绪 = happy
ExpressionDirector
   ├─ 查能力快照（CapabilitySnapshot）
   │    └─ 从模型文件动态生成：53 预设 / 7 motion / 7 表情 / 33 参数实测范围
   ├─ 按情绪筛候选（PRESET_EMOTIONS）
   │    └─ 开心 → [灿烂笑容/咧嘴大笑/咯咯笑/兴奋/眼睛发亮/…]  ← 12 个以内
   ├─ 调本地引擎（127.0.0.1:8077）
   │    └─ 从小组里挑一个
   └─ 回退闸（FallbackGate）
        ├─ high  → 采纳，播预设
        ├─ medium→ 采纳
        └─ low   → 不采纳，走情绪一致的兜底预设
   ↓
renderer.play_emote_sequence(preset)   ← 53 个预设，纯参数驱动
```

### 两条并行路径（互不干扰）

| 路径 | 触发条件 | 谁做决定 |
|---|---|---|
| `[action:{...}]` 标签 | LLM 自己点了动作 | LLM（尊重它的选择） |
| **表达决策器** | LLM 只给情绪，没点动作 | 本地引擎 |

**决策器只在第二条路生效**——LLM 已经点了动作就不抢。这避免了两套机制打架。

## 3. 三条实测硬约束（不要绕过）

### 3.1 候选选项必须写在 description 的**第一行**

引擎的 `to_parallel_schema_str()`（`model/core/schema.py`）只取 `description.split('\n')[0]`。

```python
# ❌ 错：选项在第二行，根本不会进 prompt
"description": "角色最直接的情绪\n从这些里选一个：开心/害羞/…"

# ✅ 对：单行，选项和描述在一起
"description": "角色最直接的情绪，从这些里选一个：开心/害羞/…"
```

**踩坑记录**：第一版把选项写在第二行，结果引擎完全看不到候选，输出全靠猜。

### 3.2 候选必须是**中文语义标签**，且**按情绪分组**

这是最关键的一条，两组实测数据：

**（a）英文裸名 vs 中文标签**（53 个候选，temp=0.2）

| 候选形式 | 结果 |
|---|---|
| 英文预设名（`blush_shy`/`eye_roll`/`giggle`） | 分辨力不足。「困」判成 `giggle`、「平静」判成 `giggle` |
| 中文语义标签（`害羞脸红`/`翻白眼`/`咯咯笑`） | 「困」→ 犯困 ✓、「生气」→ 生气瞪视 ✓ |

**（b）候选规模**

| 候选规模 | 命中 | 稳定性 |
|---|---|---|
| 53 个全给 | 6-8/9 | **不稳定**——同一输入换措辞就变（「惊讶」时而判成「打哈欠」） |
| 按情绪分组（每组 ≤ 12） | **10/10** | 稳定，prob 明显拉开 |

原因：候选集越小，每个候选的语义空间越干净。53 选 1 时模型会被「打哈欠/低头往下看」这类泛用项吸走。

**（c）建表原则：通用项不能混进情绪组**

第一版把 `blink3`/`blink_quick`/`sit` 也撒进了开心组，结果「开心强」被判成「快速眨眼」——通用项数量多、语义平淡，把专属项稀释了。**通用眨眼/坐卧类只留在「平静」组。**

### 3.3 输入必须是结构化状态，不是原始句子

| 输入形式 | 结果 |
|---|---|
| 原始中文句子（「在吗」「你今天真好看」） | 差。中性句一律判「惊讶」，prob=1.0 |
| 结构化状态（`emotion=happy, intensity=strong, cause=被夸奖`） | 好。这是本层实际用法 |

**情绪理解交给主 LLM**（它本来就在读对话，且比 1.5B 强得多），本层只做「情绪 → 动作」的翻译。

同时：`cause` 必须**短**（代码里截断到 60 字符）。长文本会让引擎自信判错——这是 `local-rlcd` README 里明示的边界。

## 4. 概率不是置信度

引擎 MODEL_CARD 原文：

> Reported probabilities are normalized model scores, **not empirically calibrated confidence**.

实测佐证：中性句「在吗」也能给出 `prob = 1.0`。

所以本层的用法是：
- `prob` **只用于相对排序**（哪个候选更贴合）
- 绝对值过 `FallbackGate` 档位判断：`high ≥ 0.85` / `medium ≥ 0.55` / `low < 0.55`
- **low 一律不采纳**，回退到情绪一致的兜底预设

「宁可不动，不能乱动」——桌宠表情错了比不动更糟。

## 5. 关键文件

| 文件 | 作用 |
|---|---|
| `core/capability_snapshot.py` | 从模型文件动态生成能力目录（预设/motion/表情/参数范围） |
| `core/expression_director.py` | 决策器：schema 构建 + 引擎调用 + 回退闸 + 决策日志 |
| `pet_mixins/perception_mixin.py` | 接线：初始化决策器 + `_direct_expression()` |
| `pet.py` | 在回复链路里调用（LLM 未点动作时） |
| `tests/test_expression_director.py` | 30 个单测（不依赖引擎在线） |
| `tools/verify_expression_director.py` | 端到端验证脚本 |

### 参数范围从哪来（一个反直觉的点）

`.cdi3.json` **只有 Id / GroupId / Name，没有 min/max**（实测 141 个参数全无范围）。

所以范围必须从**模型自己的 motion3.json / exp3.json 曲线**里量——那是建模师实际用过的取值范围，比猜的准。`capability_snapshot._curve_values()` 解析 Live2D 的 Segments 格式（linear / stepped / bezier 三种段类型）。

### 无 motion 模型的降级

`Rory` 和 `kurisu` 的 `model3.json` **既没有 Motions 也没有 Expressions 字段**——只有 29 个标准参数和一堆匿名参数。

这时：
- 快照记录 warning，不报错
- **预设仍然完全可用**（纯参数驱动，不依赖 motion 文件）
- 「用模型自带的动作文件」这条腿在这个模型上就是没有的——候选清单必须按模型动态生成，不能写死

## 7. 实测结果

### ⚠️ 7.0 重要更正（2026-09-20 晚，奥菲莉娅）

**本节下面的 12/12 表格是无效验证，不要引用。**

原因有两层，都是「单测全绿但功能是死的」：

**（1）接线错了：情绪恒为 neutral**

验证脚本 `verify_expression_director.py` 是**直接把情绪词喂给 `decide()`**，
绕过了真实链路。而真实链路上：

- LLM 主链路输出的是 `[feel:valence,arousal]`（VA 坐标）
- `[emotion:xxx]` 标签**只有兜底才补，补的就是 neutral**
- 实测（`tools/verify_emotion_wiring.py`）：带 `[feel:]` / `[action:]` 的样本，
  `parse_emotion` **全部返回 "neutral"**

所以决策器永远收到 neutral → 只能选「平静」组预设。
**53 个预设里那 40 多个，一个都点不到。**

**（2）引擎决策端点不可用**

`is_available()` 探的是 `/api/presets`（秒回），而真正决策走 `/api/run-rlcd`。
实测（`_tmp_probe2.py`，三次全撞满）：

```
run1: 60037ms FAIL -> TimeoutError: timed out
run2: 60008ms FAIL -> TimeoutError: timed out
run3: 60008ms FAIL -> TimeoutError: timed out
```

引擎日志里**只有 `/api/presets` 和 `/openapi.json`，没有任何 `/api/run-rlcd` 记录**
——请求到达了，但推理卡住（uvicorn 的 access log 要响应完成才写）。

**健康检查探错了端点**，所以「在线」是假象，每次决策都要撞 8 秒超时。

**（3）而且它是同步阻塞、跑在主线程**

`engine_reply_signal.emit` → Qt 队列 → **主线程** `_do_engine_reply`
→ `_direct_expression` → `decide()`。

引擎卡死时，**每次对话回复都会卡满 8 秒**。

## 8. 明确不做

- ❌ **不用引擎读原始对话**——中文理解是它的弱项，那是主 LLM 的活
- ❌ **不用它做跨段聚合判断**（如「整段是否包含 X」）——`local-rlcd` 实测不可靠
- ❌ **不把长文本喂进去**——会自信判错（`cause` 截断到 60 字符）
- ❌ **不替代 `[action:{...}]`**——LLM 点了动作就尊重它，本层只在它没点时补位
- ❌ **不引入官方 Jev**——要 API key + 付费，且中文同样弱（见 `本地决策引擎接入计划` 第 1 节）
