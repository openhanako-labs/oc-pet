## 0. 一句话结论

本地决策引擎适合给 oc-pet 补**「反应层的快速窄判断」**——屏幕变化要不要理、现在该不该开口、这句该配哪个表情/动作。
它**不替代 Hana 的对话 LLM**（那是脑），只做翻译层里那些「值不值得叫醒大脑」的前置闸门。
核心价值：**省掉大量不必要的 LLM 调用**（尤其屏幕感知 73% LLM 时间、429 限流这两个已证实的痛点）。

但有一条铁律（实测得出）：**本地模型会「自信地判错」，尤其中文长文 / 跨段聚合**。所以接入必须配**回退闸**——低置信或高风险的判断一律退回 Hana LLM。宁可不判，不能瞎判。

---

## 1. 为什么是本地引擎（相对官方 Jev / 相对 LLM）

| | 本地引擎 | 官方 Jev | Hana LLM |
|---|---|---|---|
| 成本 | **免费**（本机 GPU） | $42/十亿 input | 按量，较贵 |
| 延迟 | ~200ms（短文本） | 70–500ms | 秒级 |
| 校准 | ❌ 非校准 | ✅ 宣称校准 | — |
| 中文 | ⚠️ 弱，长文会自信判错 | ⚠️ 官方称 CJK 准确率较低 | ✅ 强 |
| 部署 | 本机服务（3GB 显存） | API key | 已在 Hana 服务端 |

**结论**：oc-pet 是本地 Python 进程，调本机 8077 最省事、零成本；凡涉及中文理解深度、跨段聚合、高风险动作的，走 Hana LLM。**官方 Jev 暂不引入**（要 API key + 付费，且中文同样弱，性价比不占优）。

## 2. 接入点候选（按 ROI 排序）

### P0 — 屏幕感知的「显著性闸门」（直击 73% LLM 时间 + 429）
- **现状**（缺口文档 G5/O1）：一次屏幕变化 = 两次 LLM 调用（vision + enrich），三消费者并发无信号量，429 无退避。
- **接入**：屏幕变化时，先用本地引擎做**原子判断**，只有通过闸门的才叫醒 LLM：
  - `is_significant_change`(bool)：这次画面变化是否值得反应（过滤光标/进度条/时间戳抖动）
  - `change_category`(enum)：[游戏进度 / 战斗 / 菜单 / 报错 / 社交媒体 / 无意义]
  - `needs_user_attention`(bool)：是否该主动提醒用户
- **收益**：大幅削减 vision/enrich 调用次数 → 直接缓解 429 与 73% 时间。**风险最低**（只读判断，错了顶多漏一次提醒）。

### P0 — 主动对话的「开口闸门」（ProactiveScheduler）
- **现状**：`ProactiveScheduler` 967 行，用 LLM 决策该不该开口，成本高。
- **接入**：先用本地引擎判断：
  - `should_speak_now`(bool)：现在是否适合主动开口（静默/专注/离开语境时不打扰）
  - `speak_intent`(enum)：[闲聊搭话 / 提醒 / 共情 / 吐槽 / 不问]
  - `urgency`(enum)：[现在 / 稍后 / 别打扰]
- **收益**：把「要不要开口」这类高频、低风险判断本地化，省 LLM。低置信时回退 Hana。

### P1 — 表演动作选择（解 G6「模型猜动作名」幻觉）
- **现状**（缺口文档 G6/A2）：`[do:名称]` 由 LLM 自由生成，归一靠别名表，无白名单约束 → 幻觉。
- **接入**：把**已加载的 motion/表情目录当 choices**，用本地引擎从白名单里**选**（choice 原语天生就是「从给定集合挑一个」）：
  - `action_id`(enum)：从 motion 目录快照里选
  - `emotion`(enum)：从 face 9 类里选
  - `mouth_intensity`(enum)：[轻 / 中 / 强]
- **收益**：**根治幻觉**——引擎只能从白名单选，不会编不存在的动作名。这与官方 AgentAtelierR 的 `motionGroups` 快照思路一致。
- ⚠️ 边界：目录超过 ~255 项要分批（引擎上限 255 choices/字段）。

### P1 — 工具路由初判
- **现状**：三层工具（本地能力 / Hana 目录 / Node 插件）。
- **接入**：`tool_layer`(enum)：[本地能力 / Hana / Node插件 / 不需要工具] + `needs_tool`(bool)。
- **收益**：省掉「先问 LLM 再路由」的一次调用。

### P2 — 口型/情绪参数粗分类（O3 相关）
- 用本地引擎做粗档情绪分级，精细时序仍由现有 lip_sync 三级回退负责。收益一般，优先级低。

## 3. 架构选项（**推荐 A**）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 独立本地服务** ✅ | oc-pet 通过 HTTP 调 `127.0.0.1:8077` | 崩溃隔离、显存独立、可单测 | 需常驻一个进程（显存 3GB） |
| B 进程内 import | oc-pet 直接 `from client import decide` | 无网络 | 3GB 模型进 oc-pet 进程，增负担+耦合 |
| C 作为 oc-pet 的 MCP 工具 | 在 9 个 `pet_*` 工具里加一个 `pet_decide` | 对外统一、可给其他 agent 用 | 依赖 MCP 提供端（默认关） |

**推荐 A + 后期补 C**：先独立服务跑通，再把「决策」封装成一个 MCP 工具对外暴露（顺带解缺口文档 O2「MCP 提供端补强」的一部分）。

**常驻策略**：默认**不常驻**——oc-pet 首次需要时 lazy 启动该服务（子进程），空闲 N 分钟自动停，避免一直占 3GB 显存。启动脚本已有 `start_server.ps1`。

## 4. 关键设计：回退闸（必做，不是可选）

因为本地模型「自信地判错」，接入层必须包一层闸门：

```
本地引擎给 (value, prob, band)
        │
        ├─ band=high 且 risk=low   → 直接采用
        ├─ band=medium             → 采用，但记录待观察
        └─ band=low 或 risk=high   → 回退 Hana LLM（或直接不动作）
```

- 阈值可调：`RLCD_CONF_HIGH` / `RLCD_CONF_LOW`（env）。
- **高风险动作**（切游戏内操作、发消息、改配置）即使 high 置信也应走确认，不自动执行。
- 记录每次决策的 `(source, field, value, prob, band, action)` 到日志，供后续校准——这正好补缺口文档 O1 里「日志埋点」的诉求。

## 5. 分阶段落地（建议）

| 阶段 | 内容 | 风险 | 依赖 |
|---|---|---|---|
| **阶段 0** | 服务化 + 回退闸封装 + 日志埋点（本轮已备好 `client.py`） | 低 | — |
| **阶段 1** | 接 P0 屏幕感知显著性闸门（只读判断） | 低 | 阶段 0 |
| **阶段 2** | 接 P0 主动对话开口闸门 | 中 | 阶段 0 + ProactiveScheduler 改造点 |
| **阶段 3** | 接 P1 动作选择（白名单从 motion 目录生成） | 中 | 动作目录快照（缺口文档 A2） |
| **阶段 4** | 封装成 `pet_decide` MCP 工具对外暴露 | 中 | 阶段 0 + MCP 提供端补强（O2） |

**首个验证用例**：阶段 1 的 `is_significant_change`——最安全、最省 LLM、最容易量化收益（对比接前/接后的 vision 调用次数）。

---

## 6. 非目标（明确不做）

- ❌ 不用本地引擎替代 Hana 对话 LLM（脑在 Hana，不动）。
- ❌ 不自研独立 agent 循环（oc-pet 的翻译层选型保持）。
- ❌ 不引入官方 Jev（付费 + 中文同样弱，本地够用）。
- ❌ 不把长文档/大段中文喂给本地引擎（会自信判错，见第 0 节铁律）。
- ❌ 不用它做跨段聚合类判断（如「整篇是否包含 X」）——实测不可靠。

---

## 7. 风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| 自信判错 | 中文/长文 prob 高但答案错（实测） | 回退闸 + 只用于窄判断 + 日志校准 |
| 显存占用 | 常驻 3GB | lazy 启动 + 空闲自动停 |
| 延迟 | 长文本 80s（实测） | 严格限长 + 切块 + 只喂短 context |
| 校准缺失 | prob 非真概率 | 不把 prob 当正确率；阈值用自己数据调 |
| 进程管理 | 派生子进程难杀 | 启动脚本记录 PID，提供停止命令（README 已写） |
