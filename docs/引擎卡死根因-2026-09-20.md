# 引擎「卡死」根因报告

> 作者：奥菲莉娅（Ophelia）
> 日期：2026-09-20
> 对象：`projects/local-rlcd`（本地 RLCD 决策引擎）
> 结论：**不是死锁，是显存耗尽退化。环境问题，代码无需改动。**

---

## 0. 结论

`/api/run-rlcd` 在 60 秒超时，**不是引擎坏了，也不是锁死**。

是**显存不足时 CUDA 回落到 Windows 共享内存**，单次推理从 ~100ms 掉到 30 秒以上——
看起来像卡死，实际是极慢。

本机是 RTX 3060 **Laptop**，只有 **6GB** 显存，而同时跑着：

| 占用方 | 说明 |
|---|---|
| 本地引擎（Qwen2.5-1.5B） | ~3.4 GB |
| 桌宠（Live2D 渲染） | 数百 MB |
| 19 个桌面应用 | 浏览器 / Steam / QQ / KOOK / PotPlayer / Magpie… |

实测引擎 idle 时，6GB 已被占到只剩 **1929 MB** 空闲。

---

## 1. 决定性实验

逐步吃掉显存，每步测一次引擎延迟：

```
压测前 vram(used,free) = 4054, 1941
  基线:            130ms OK
  已占  512 MB:    100ms OK     (free 1304)
  已占 1024 MB:    119ms OK     (free  792)
  已占 1536 MB:  30032ms TIMEOUT (free  472)  ← 退化点
  已占 2048 MB:    791ms OK     (free  408)  ← 部分恢复
释放后:            116ms OK
```

**剩余 472 MB 是退化点。** 30 秒超时不是「卡死」，是推理真的在跑，只是慢了两个数量级。

---

## 2. 排除项（都实测过）

| 假设 | 实测 | 结论 |
|---|---|---|
| 引擎本身有 bug | 单发 236ms / 103ms | ❌ 排除 |
| 并发死锁 | 并发 6 路全成功（串行化） | ❌ 排除 |
| `_gpu_lock` 锁泄漏 | 放弃 SSE 流 / compare / run-naive / run-tree 后引擎仍正常 | ❌ 排除 |
| 长时间退化 | 压测 **1120 次**（10 分钟），均值 ~120ms，**0 失败** | ❌ 排除 |
| 空闲后无法唤醒 | 空闲 45s 后首请求 128ms | ❌ 排除 |
| schema 太复杂 | 桌宠真实 3 字段 schema × 15 次，最慢 283ms | ❌ 排除 |
| 网络 / 代理 | 无代理，`no_proxy` 含 127.0.0.1 | ❌ 排除 |
| 驱动崩溃（TDR） | 事件日志无 4101 / nvlddmkm 记录 | ❌ 排除 |

---

## 3. 为什么日志里看不到记录

uvicorn 的 access log 在**响应完成后**才写。请求超时断连后，那一行永远不会出现。

所以「日志里只有 `/api/presets`，没有 `/api/run-rlcd`」**不代表请求没到达**——
它到达了，只是没跑完。

而 `/api/presets` 是**纯 CPU** 的（只读 JSON 文件），永远秒回。
这就是 `is_available()` 的盲区：**健康检查探的端点不碰 GPU**。

---

## 4. 时间线还原

旧进程（pid 30616）的 `server.out.log`：

```
Loading ... on cuda (torch.bfloat16)...
Engine ready.
GET  /api/presets          200     ← 探测
POST /api/run-rlcd         200  ×12  ← 对方 12/12 验证，全部成功
GET  /docs                 200
GET  /api/presets          200  ×N   ← 桌宠 is_available() 反复探
GET  /openapi.json         200
（之后无 run-rlcd，我的三次请求全超时）
```

**12 次成功 → 桌宠启动 → 之后全挂。**

桌宠启动后占了显存，把引擎挤过退化点。

---

## 5. 已做的处置

1. **熔断**（`pet_mixins/perception_mixin.py`）：即使撞到也只卡一次，
   连续失败 2 次停用 300 秒。避免每次对话都卡。
2. **`config.json` 保持 `enabled: false`**：6GB 笔记本上跑不动
   「1.5B 模型 + Live2D + 桌面应用」三件套。
3. **引擎已停止**：释放约 3.4 GB 显存（显存占用从 4066 MB 降到 641 MB）。

## 6. 要真正启用，可选的路

| 方案 | 代价 | 说明 |
|---|---|---|
| 换显存更大的机器 | 硬件 | ≥12GB 才宽裕 |
| 用更小的模型 | 精度 | 0.5B 级别，中文理解会更差 |
| 决策前先释放桌宠 GPU 资源 | 复杂 | Live2D 渲染不能停 |
| **把情绪判断交回主 LLM** | 改接线 | **最推荐**——见下 |

### 为什么不建议继续在本地引擎上做情绪识别

同日两条独立线索都指向同一结论：

- 对方的对照实验：**几何最近邻 3/9**（VA 空间最近邻）
- 我的复核：**手写阈值规则**在日志真实样本上把「关心」判成「开心」

方法不同，结论一致：**VA 二维坐标承载不了中文对话的情绪细粒度**。

而主 LLM（Hana）读懂对话的能力远强于本地 1.5B。让它直接输出情绪词，
比在 VA 坐标上做文章靠谱得多——本地引擎的定位应退回到
「**已知情绪，挑具体表情**」这一跳（那是它擅长的，实测 10/10）。

## 7. 一句话给下一个人

**引擎没坏。是 6GB 显存装不下「1.5B 模型 + Live2D + 19 个桌面应用」。**

要验证引擎本身，先关掉桌宠和占 GPU 的应用，再跑：

```powershell
cd W:\Games\Hanako\Work\projects\local-rlcd
.\start_server.ps1
# 另开一个窗口
curl -X POST http://127.0.0.1:8077/api/run-rlcd `
  -H "Content-Type: application/json" `
  -d '{\"context\":\"开心\",\"schema\":{\"e\":{\"type\":\"enum\",\"description\":\"情绪\",\"choices\":[\"开心\",\"难过\"]}}}'
```

正常应返回 ~100-300ms。
